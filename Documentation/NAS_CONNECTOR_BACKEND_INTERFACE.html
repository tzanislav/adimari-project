NAS Connector and Backend Interface Inventory

Source of truth: current backend routes and services, inspected 2026-08-14.

This is an implementation inventory: it describes what the backend currently

accepts and does, including paths which are still mentioned by the UI or older

documentation but are no longer implemented.

Direction of communication

The backend does not open an HTTP, WebSocket, or named-pipe connection to the

Windows Connector. The Connector initiates every connection:

Connector  -- HTTPS request -->  Backend
Connector  <-- HTTPS response -- Backend

The backend asks the Connector to do work by adding/changing a durable job.

The Connector sees that work only in the response to its next polling request.

Browser/admin actions are therefore indirect backend-to-Connector requests.

The storage transfers are separate from backend HTTP:

Browser    -- signed multipart URLs --> S3 staging
Connector  -- signed GET or PUT URL -> S3 staging/cache/thumbnail
Browser    <-- signed download URL -- S3 cache/thumbnail

The backend creates short-lived S3 URLs and does not proxy file bytes. It

stores only database IDs, logical root IDs, safe relative paths, and metadata.

It never receives or returns a native Windows/UNC NAS path.

All NAS routes exist only when NAS_CONNECTOR_ENABLED is exactly true. Otherwise

/api/nas-connectors and /api/nas-catalogue are not mounted.

Common protocol, security, and schemas

Credentials

CallerHeaderApplicable requests
New/reconnecting ConnectorAuthorization: ConnectorKey followed by 43-char base64url shared keyPOST /connect only
Enrolled ConnectorAuthorization: Connector followed by its 24-hex Mongo connector IDevery other Connector control request
Browser/adminAuthorization: Bearer followed by Firebase ID tokencatalogue and administrator requests
Public share userNo Firebase token; raw 43-char share token is in URL/download/:token requests

Connector routes require HTTPS unless NAS_CONNECTOR_ALLOW_HTTP=true. The shared

key is accepted only at /connect; it is not stored or rechecked on heartbeat,

poll, acknowledgement, or job calls. The active connector ID is therefore a

bearer credential after enrolment. Revocation makes it unusable.

The JSON request limit is 1 MiB. Heartbeat, polling, and acknowledgement have

a 120 request/minute production limit (1,000 development). NAS catalogue

requests are limited to 1,000/minute/IP in production (5,000 development).

An admin may exempt one exact literal IPv4/IPv6 address from this catalogue

limiter only.

Normal Connector errors are:

Bad, unknown, disabled, and revoked Connector credentials all receive the

same 401 NAS_CONNECTOR_UNAUTHORIZED response. Unexpected Connector failures

are redacted as NAS_CONNECTOR_OPERATION_FAILED and do not log request bodies.

Connector to backend: every accepted request

Base URL in this section is /api/nas-connectors. Every route needs the

enrolled Connector header except POST /connect, which needs ConnectorKey.

Folders require sizeBytes null and previewKind none. Files have non-negative

Each watcher change is exactly:

{ "operation": "upsert", "entry": { ...the exact index entry... } }

or:

{
  "operation": "delete",
  "relativePath": "Designs/old-folder",
  "recursive": true
}

Duplicate paths in one batch fail. Recursive deletion soft-deletes the target

and descendants. A version change makes cache/thumbnail state stale. A full

scan cannot delete a watcher observation newer than that scan.

Backend actions which create Connector work

No backend-to-Connector HTTP route exists. The following modify durable

backend state; Connector learns of job/cancellation through poll or its later

job request.

Security controls and current limitations

Controls:

Startup fails closed on invalid NAS/File Server configuration.
HTTPS is default; HTTP requires NAS_CONNECTOR_ALLOW_HTTP=true.
Shared key is used only on /connect and checked by backend secret helper.
Revoke disables roots and blocks subsequent Connector control calls.
Admin needs Firebase admin; catalogue needs Firebase admin/moderator.
IDs, paths, batch size, filenames, MIME types, fingerprints, and ack are bounded.
Browser staging, Connector cache, and thumbnail use private non-overlapping S3 prefixes.
Connector gets signed GET only after upload/start; cache/thumbnail get signed PUT.
Native paths/AWS credentials are not sent to Connector or browser.
Public tokens are random 32-byte values; DB stores SHA-256 hashes only.
Public download is no-store/private/no-referrer. Helmet, CORS, body/rate

limits protect backend HTTP. CORS does not authenticate a Connector.

Limitations:

An active connector ID alone is accepted after enrolment; it is not an HMAC,

secret proof, or expiring credential. A leaked ID can impersonate that

Connector until revoke.

No audit read endpoint and no admin clear for cache/write-upload. Admin

cancellation is only index/thumbnail.

Revoke blocks later API calls but does not actively terminate NAS work

already started locally.

Development reset is destructive across shared prefixes.
Retention is periodic/TTL based, not immediate deletion.

Fast investigation guide

Unexpected Connector work must come from a job caused by: admin index request,

local index request, browser thumbnail, browser open/download/share, or

browser upload completion. Connector can receive it only on its poll response.

Unexpected backend change without visible user action is likely stale-liveness

reconciliation during admin listing, poll-time lease/watchdog recovery,

retention sweep, or development reset. None sends unsolicited network traffic

to Connector.
